# Sprite tools: getting off the pixel-by-pixel loop

Investigation of 2026-10-19, after Hellfire took 14 rounds of frames (v1 to v14) to get one look right. This page is a
decision page: what slowed us down, what the mod already offers, which outside tools fit, and what is still open.
Anything marked *unverified* comes from the tool makers' own pages and has not been tried here.

## Why Hellfire took 14 rounds

Hellfire was a **recipe**, the art as code (`LooksHellfire.cs`, gone 2026-10-19 evening); it is a **pack drawn over the donkey** now, generated by `tools/skins/hellfire/make_hellfire.py` from the same reviewed prototype (`hellfire_proto.py`, kept there) with the erase colour and the `[Base.Coat]` recolour (docs/skins.md) doing what only code could before. Every
change went the same long way: you describe what is wrong in words, I change numbers in code, render 44 frames,
you look at PNGs, you describe the next thing. Nobody ever drew a pixel and saw the result. The slow part was not
the drawing; it was that every fix crossed from picture to words to code and back. Horns that "should sit where
they are in ear 02 to 04" are one drag in an editor and three rounds in code.

So the fix is to put the art where you can see what you change, and keep code only for what has to be code.

## What the mod already has (no new tools needed)

- **Packs of pictures** (docs/skins.md): a PNG per frame (44, named `bdy_walk_left_01.png` and so on) or one
  `sheet.png`, 96x96, facing left, feet on row 64, back on row 41. A frame left out shows the donkey's own, and
  `bdy.png` / `bdy_walk_left.png` fill all the undrawn body or walk frames.
- **`layer = over`**: pictures drawn **on top of** the donkey (a saddle, a hat). Horns, a devil tail, cracks and
  glowing eyes are additions, so they fit here, and an overlay has no game pixels in it, so it can be shipped.
- **Templates**: the 44 game frames exported at full size by the asset probe's "Export frames"
  (`BepInEx\GK2-asset-probe\donkey-frames\`). Paint on a layer over them; export only your layer.
- **Reload in game** (dev panel, the skin's rows, "Reload from the file", `Dev/TuningWindow.Mounts.cs:403`): reads
  `skin.cfg` and **the pictures again from disk** (checked in code: the pack's reader opens each file fresh). The
  list of file names is taken when the game starts (packs are scanned only then, `Looks.cs:345`; the "reload
  folders" of skins-design.md was never built), so a frame file added after start needs a restart; a pack with one
  `sheet.png` never has that problem.

Draw, save, press reload, look: seconds per round instead of a round of messages.

## The one gap: taking pixels away

`layer = over` only adds. Hellfire also **erases** the donkey's tail, **refills** the rump curve and **recolours** the
coat to ash. An overlay can't do the first two, and `layer = replace` means repainting the whole donkey, which can't
be shipped because the donkey's pixels are the game's.

How the work would split:

| Part of Hellfire | Paintable as an overlay today | Needs code |
|---|---|---|
| Horns, devil tail, lava cracks, glowing eyes | yes | |
| Ash coat (recolour) | | yes, but it is one colour rule, not shape work (it never needed a round) |
| Donkey tail erased, rump curve filled | | yes: this was the shape work |

**Decision for you:** a small extension would close the gap, for example an overlay pixel of one reserved colour
(say pure magenta) meaning "clear the donkey here", with the rump fill painted as normal overlay pixels. Rough cost:
a short addition in the pack loader and the sheet builder, a self-test, a skins.md section. Not built; your call.
Without it, the split is: shapes painted, erase and recolour stay in the recipe.

## Outside tools

Two different users: **you drawing** (an editor), or **me drawing** (a tool I can drive instead of pixel maths).

### Editors for you

| Tool | Cost | What matters for us |
|---|---|---|
| **Aseprite** | about $20 (Steam or aseprite.org) | The reference pixel editor. Layers (template locked underneath), **onion skin** (see the frames before and after), **tags** per animation (walk, ear, graze...) with a looping preview, **linked cels** (draw a horn once, it is in every frame; move it per frame where the head moves). Command line and Lua scripting for batch export ([CLI docs](https://www.aseprite.org/cli/)), so export to the pack folder can be one command. Most AI plug-ins target it. |
| **Pixelorama** | free (MIT) | Layers, onion skin, cel linking, timeline ([review](https://scribe.disroot.org/post/2025114)). The free choice; PixelLab's extension supports it too. *Unverified here.* |
| **LibreSprite** | free | Fork of an old Aseprite; core features close to it, onion skin not confirmed in what I found ([alternatives](https://www.alternativeto.net/software/aseprite/)). Behind Pixelorama for us. |

None of these was found in the usual places on this machine (Program Files, Steam, PATH; an itch.io or portable
copy under your profile would not show).

**The Aseprite trial (tested 2026-10-19, v1.3.18.6-trial):** opens and edits files, but every save and export is
refused ("Save operation is not supported in trial version"; tried from the command line, where a
`--sheet` export writes the JSON data but not the PNG), and the `--script` option is missing. So the trial is for
judging the editing, not for making a pack. A starting file for that, built by script without Aseprite's help:
a `hellfire.aseprite` (96x96, 44 frames in pack order; layers "donkey (game)" and "Hellfire v14" locked, "draw
here" open; tags static, walk, ear, graze, chew, lips, turn, head; built from the harness frames by a `make_ase.py`,
both retired 2026-10-19 23:30 with the old canvas: `tools/skins/ase_write.py` writes such a file from any generator,
Royal Parade's `out\royal.aseprite` is the live example). Aseprite read it back with the right layers and tags.

**Built from source (2026-10-19):** the EULA allows compiling for your own use (EULA 2(g); not to be passed on). Built with VS 2022
Build Tools at `C:\Users\User\Documents\GitHub\aseprite\build\bin\aseprite.exe`: the full version, with saving, export, the command line
and Lua scripting. Exporting the "Hellfire v14" layer of `hellfire.aseprite` as a sheet gives the game's Hellfire frames
exactly (44 frames, 0 pixel differences). Command-line note: `--layer` goes before the file name. What was installed
where: `C:\ClaudeCodeTemp\GK2-aseprite\INSTALL-LOG.md`.

Recommendation: **Aseprite** if $20 is fine (linked cels plus the command line are exactly what a 44-frame overlay
needs); **Pixelorama** if it should be free.

### AI generators (only worth a small test)

- **PixelLab** ([site](https://www.pixellab.ai/)): AI pixel art with "animate with skeleton", "animation to
  animation" and an "Edit animation (Pro)" tool that needs at least 2 frames and runs only inside the Aseprite and
  Pixelorama extensions ([docs](https://www.pixellab.ai/docs/tools/edit-animation-pro)). Its consistency claims are the
  makers'. Our frames carry the head inside the body and must keep feet and back on fixed rows, which is exactly where
  such tools slip. If tried: the 8 walk frames only, checked with the compare scripts, not all 44.
- **Retro Diffusion** ([itch.io](https://astropulse.itch.io/retrodiffusion)): image generation inside Aseprite,
  $20 lite / $65 full, one-time. Better for new creatures from scratch than for editing ours. Noted, not suggested.

## Proposed workflow

1. You pick an editor (Aseprite or Pixelorama).
2. I build the starting file: the 44 game frames as a locked bottom layer, grouped into tags per animation, and
   Hellfire's current horns, tail and cracks (from the v14 output, game pixels removed) as editable layers. Fixing
   Hellfire then starts from what you reviewed, not from scratch.
3. You draw and move things by eye, with onion skin and the loop preview.
4. Export into `BepInEx\plugins\gk2skins\<id>\` as one `sheet.png` (so reload always works; the folder is
   `gk2mounts\<mount>\skins\<skin>\` since 2026-10-24); in Aseprite I can make that one command or a button.
5. In game: dev panel, "Reload from the file", look.
6. I check what you exported before you look in game: sizes, feet and back rows, transparency, stray colours, no game
   pixels left in the overlay. That catches the mechanical errors, so your rounds are only about looks.

The erase and recolour stay in code until you decide on the extension above.

### Making a skin: the one pipeline (2026-10-19 23:00; the tools finished 2026-10-20, the plan's M6)

Every skin we ship is a **built-in pack** and goes the same way (the user: "we need to make them the same since
they will both be included", "once we set up this pipeline we can keep following it to create more skins for
other mounts too"). Hellfire and Royal Parade (over the donkey), the four creatures and Gerry (a game character)
are the worked examples; the next skin or mount is **scaffold, generate or draw, check, look, build, export**:

1. **Scaffold**: `python -I tools/skins/new_skin.py <skin> [--mount <mount id> --name "..."] [--canvas 128] [--seat 62]
   [--over] [--mod <project> | --pack <Pack>]` makes `src/<project>/assets/mounts/<mount>/skins/<skin>/skin.cfg` (an
   external pack: `packs/<Pack>/gk2mounts/<mount>/skins/<skin>/`, docs/making-a-mount.md "Built in or external") in the canonical
   layout (the mount is `donkey` without `--mount`; the project is `SaddleUp` by default, which ships every mount and
   skin, or a mount mod of its own that embeds and registers its packs as Saddle Up does; docs/mounts-as-mods.md)
   (`seat = <row>`, a `[Colors]` stub), and for a mount with no folder yet the mount folder and its `mount.cfg`
   (`[Mount]` with the speed and cargo, a `[Sounds]` stub; the mount id is `<mod>.<name>` and its own look the skin
   `default`, so a new mount starts with `new_skin.py default --mount me.giant-crab`),
   `tools/skins/<id>/make_<id>.py` (a generator stub drawing a placeholder in every frame through the shared review
   module), the `.gk2export.txt` sidecar for Aseprite, runs the stub and the scan. Nothing else to set up.
2. **Generate or draw.** The generator (`tools/skins/<id>/make_<id>.py`) reads the base's frames as the game places
   them (`gamedir.donkey_frames()`, the asset probe's export; never the raw harness frames) and draws or computes the
   skin's pixels per frame on that canvas; measurements it needs (anchors, horn bases) are data files next to it,
   each with the script that measured them. Every generator writes its pictures for the eye through
   `tools/skins/review.py` (`write_all`): `out\strips\<animation>.png` (every animation as a strip, the front layer
   composited, the rider on the seat row: **look at every strip before the game does**), `out\preview.png` (all 44
   frames) and `out\pack\sheet.png` (the cells, for Aseprite). The four creatures share one generator
   (`tools/skins/creatures/make_creatures.py [name]`, `out\<name>\`), Hellfire and Royal Parade have their own.
   Drawing by hand instead: open the `.aseprite` (or make one with `ase_write.py`), save, and `watch_skin.py` exports
   the sheet and **splits it into the per-frame PNGs** of the folder the `.gk2export.txt` sidecar names (`front.png`
   into `front\`), runs the checker and writes previews with the front layer and the rider (the round below). A
   hand-drawn skin's sidecar names the built-in's folder; a generated skin's (Royal Parade) names its `out\pack`, so
   the generator stays the source and carries the fix (its next run would overwrite the folder anyway).
3. **The pack** is `src/<project>/assets/mounts/<mount>/skins/<skin>/` (built in) or
   `packs/<Pack>/gk2mounts/<mount>/skins/<skin>/` (external), with the mount's `mount.cfg` and `sounds\` in the mount's
   folder (`tools/skins/skinroots.py` knows every such root, mount and skin): `skin.cfg` (by
   hand, commented, kept by the generator, in
   the layout `tools/skins/canonical_cfg.py` writes: `layer = over` for a skin drawn over the base, `erase` when it
   takes parts off, `[Base.<Region>]` to recolour the base under it, `[Colors]` for the regions the player's colours
   reach (written from the pixels by `tools/skins/skin_colors.py`, whose rules are data in
   `tools/skins/creatures/colors.json`: a block per skin, hue, saturation and value thresholds per region, Gerry's from
   the game's export), `seat = <row>` for the canvas row the rider's hip sits on (52 on the 96 canvas is the donkey's
   own seat; `+16` on 128), the skin's own geometry in `[Tuning]` / `[Tuning.Ride]` / `[Tuning.Cart]` (`HitchGapPx`,
   `RiderOffsetPx`); no `id =` line (the folder's name is the skin's) and no `[Mount]` section: a creature of its own
   has its `mount.cfg` with id, name, author, version, cart, foals, the creature's facts and its sounds) and **a PNG per frame key**
   (`bdy_static_left.png` ... `hed_static_down_03.png`, `front\` for the layer drawn in front of the rider), only our
   pixels, nothing of the game's art. A built-in one: the DLL build embeds the folder (the project's csproj,
   `assets\mounts\**`: `SaddleUp.csproj` for Gerry). An external one (the dragon, the critters, the donkey's two skins
   in `packs/SaddleUpDonkeySkins/gk2mounts/donkey/skins/`): its own small DLL embeds
   it (`packs/<Pack>/<Pack>.csproj`, `gk2mounts\**`); no file of the pack is copied into the game either way, the DLL
   carries them.
4. **Check before the game**: `python -I tools/skins/check_skin.py <the skin's folder>` (frames and
   the front layer present and the canvas size, every colour with its region, the erase marks, lone pixels judged
   over what the game draws under them, half-transparent pixels; an exit code for the scans, the warnings for the
   eye), `python -I tools/skins/canonical_cfg.py --check` (the layout) and the headless scan `dotnet run --project
   tests/SkinsScan -c Release` (every key and value the loader reads, the pictures, the seat row on the body, the
   `[Colors]` lists against the pixels, every `mount.cfg` and its rules); `tools/release-scans.sh` runs all three
   on every built-in (the checker reads the asset probe's `donkey-frames\` export under an over skin, so that export
   must exist on the machine running the scans).
5. **Look**: the review page (`python -I tools/skins/skin_preview_html.py <probe folder> <probe
   folder>/skins-preview.html`), every frame through the same composite the game makes, grouped by mount, the front
   layer in front of the rider, the rider on the seat row with the skin's offset, the seat line, the card's facts
   (seat, hitch gap, babies, colour regions). **Before anyone else looks** (the dragon's wings, 2026-10-20: twelve
   drafts, every one judged "done" by the person who drew it and sent back by the user): render the standing and a
   walk frame at 1x and at the page's 3x, with and without the rider, next to the reference crop at the same scale,
   and answer these in writing, not "it reads": where does the part attach to the body, and is that where it
   attaches on the reference; do the two sides of a pair share one root and shape, offset only by perspective; what
   is the silhouette's signature (a wing: the peak above the shoulder with the claw hooking forward) and is it
   there; is the colour apart from the body's; is anything on the wrong part of the body (a wing on the rump, a
   fold on the tail); with the rider, what exactly is covered and what is in view; and name every difference from
   the reference that is left. A draft that only confirms what was intended is not a check.
6. **Build and deploy** with the game closed (`dotnet build src/SaddleUp/SaddleUp.csproj` for Saddle Up's packs); the self-tests
   (F11, Tests tab, "Skins and effects") cover the drawing with readbacks; wear it, walk, turn, graze; then "Export the
   loaded skins as built" (F11, Mounts tab: every skin loaded at that moment) and rebuild the page: it shows the game's
   own export and counts where its composite would differ (0 = the page shows what the game shows).

Another game character as a mount (Gerry) is the by-hand path: `tools/skins/gerry/gerry_probe.py <game folder> <out>
[<prefix>]` finds the addressables bundle holding `<prefix>bdy_walk_left_01` and exports the character's sprites,
`gerry_sheet.py <frames> [<prefix>]` lays them out for measuring, and the skin is a `skin.cfg` alone (`source = game`,
`[Game]` with the prefix, scale, lift and the frame map; docs/gerry-mount.md). A skin drawn **over** one of our own
creatures needs that creature as a base (`base = rat` ...): the loader has one base today, the donkey (`SkinBase`),
so that is the next piece of machinery when the first such skin is wanted.

A round:

1. Open the skin's `.aseprite` (Royal Parade: `tools/skins/royal-parade/out/royal.aseprite`, regenerated by every `make_royal.py` run). Layers: `donkey (game)` locked at the bottom (the reference, never exported),
   then the skin's parts, one layer each (Royal Parade: `caparison`, `crown`); a tag per animation.
2. Fix what is wrong by eye: Enter plays the tag, F3 shows the frames before and after, Move (V) drags a part in
   one frame. A part redrawn once goes to the rest of its tag with **File > Scripts > GK2 Part to all frames**
   (each frame keeps where its own copy sat, lined up by the bottom centre).
3. **File > Scripts > GK2 Export skin**: every visible layer except the donkey into the pack's `sheet.png`
   (layers named `front...` into `front.png`), then the checker's verdict in the same window. The pack folder and
   the check command are in `<name>.gk2export.txt` next to the `.aseprite` file. The first time, Aseprite asks
   whether the script may save a file and run a command: choose "Give full trust to this script" both times. New
   scripts show in the menu after File > Scripts > Rescan Scripts Folder (or a restart).
4. In game: dev panel, the skin's rows, "Reload from the file". Look.
